| D53 | **M8 loop persistence = links to WAV files, never audio in the project (your D36, refined by your answers 2026-10-20).** Each deck has LOAD... and SAVE... on a new FILES page. **Nothing is saved automatically** (your decision: auto-save "could become a nightmare"). A deck whose loop came from LOAD or SAVE is *linked* to that file; the project stores only the link: path, path relative to the home folder (when inside it), size and a fingerprint (FNV-1a hash of the file's bytes). On project open each linked deck is loaded from its file again. If the file has moved or been renamed the home folder is searched (subfolders, up to 50,000 entries, `.wav`, same size) for the same fingerprint; a file with the same name but different audio is never taken for it unless it sits at the stored path (then it is loaded and the note says it changed). A missing file leaves the deck empty with "Missing: name (looked in folder)"; the link is kept in the project for next time. Home folder: default `~/Music/Unofficial Spotykach/`, FOLDER... button, stored per computer in `~/Library/Application Support/Unofficial Spotykach/home-folder.txt` (not in projects). | D54 | **LOAD takes any common WAV**: 8/16/24/32-bit integer, 32/64-bit float, extensible format, mono or stereo, any sample rate 1 kHz to 768 kHz. It is converted to the engine's stereo 48 kHz with the same windowed-sinc resampler as the audio path (measured: tone error under 0.01 against an ideal sine at 11.025, 22.05, 32, 44.1, 88.2 and 96 kHz), mono is copied to both sides, and the file is cut to the deck's 42 s. Cue points in the file become **slice points** (as the firmware's `wav.cpp`/`storage.cpp` do), sorted, at most 255. SAVE writes the firmware's own format (32-bit float, stereo, 48 kHz) plus a cue chunk when the loop has slice points. AIFF, FLAC, MP3 and M4A are **not** supported (WAV only). More than 2 channels and compressed WAV are refused with a message. | Mine | Not verified: whether the hardware accepts a WAV saved here (same header format as its own saves; not tried). |
| D55 | **Audio crosses between threads in 16,384-frame steps per 2 ms engine tick, through atomics; the audio thread never allocates, locks or does disk I/O** (the file is read, decoded and resampled on a worker thread; the engine copies). A 42 s load takes about 0.25 s of audio time; measured slowest `process()` call during it 0.15 to 0.46 ms (Linux, Release). Because the copy is done by the audio thread, **LOAD and SAVE only complete while the host is running audio** (Logic keeps processing when stopped, as you saw in Layers); the window says "waiting for the host to run audio" after 2.5 s. | Mine | |
| D56 | **Link lifecycle:** a recording or overdub (or arming a record, which clears the loop) drops the link and the deck shows "Not saved to a file", and it is no longer written to the project. LOAD and SAVE are refused while a deck is armed or recording. LOAD stops the deck and leaves it stopped (press Play). A failed LOAD (not a WAV, unreadable) leaves the deck as it was and shows the reason in red. SAVE needs a loop. A deck that holds audio but has no link in a project you open keeps its audio, shown as "Not saved". A project saved by an older version has no link information and leaves the decks alone. | Mine | |

## Lessons / process

- `auval` does not open the plug-in window. A green CI and a passing `auval` do not prove the editor works. A window-open test (a headless editor smoke test in CI, or opening it in Logic) is needed for every milestone that changes the UI. Proposal: add an editor smoke test to CI in M2 (unverified that it works on a headless runner).
- Intel Mac details: macOS 12.7.6 (crash report), Logic 10.7.8 (build 5817), MacBook Pro (MacBookPro11,2). Your earlier notes said 12.7; the crash report says 12.7.6.

---

- Running the engine tests on x86 caught a crash that ARM hides: `Generator::apply_dimensions()` takes a modulus by zero in Slice mode on an empty deck (ARM returns 0, x86 raises SIGFPE and would have crashed Logic on the Intel Mac). Patched, and recorded in `third_party/spotykach/NOTICE.md`. Lesson: test on x86 and under UBSan, not only on the M4.
- Your envelope observation: at minimum (0) the firmware envelope is OFF, so the playback edges are hard. The attack only becomes a ramp above about a third of the knob (`ADEnvelope::_make_shape`). I have not changed it; see the question below.

## Upstream issues found (kept for a possible report to Synthux)

1. `fx.flux.cpp:83`: initialised variable-length array; invalid in Clang.
2. `fx/deline.h`: derived from DaisySP `delayline.h` but copyright header missing.
3. `core/synclock.cpp`: Paul Messick toolkit lineage, no licence text in repo.
4. `fx/echo.h`, `fx/biquad.h`, `lutsinosc.h`: missing or partial licence headers.
5. Uninitialised members in `Core` (`_route`, `_click_mix`, `_mix`, `_mix_mod`); relies on zeroed static memory.
6. `Panner` calls `std::random_device` on the audio thread.
7. Missing standard `#include`s in several core headers (ARM headers hide it).
8. `softswitch.h`: fixed 191-step fade against a 4 ms constant; only right at 48 kHz.
9. Unused third ("undo") source buffer is allocated.
10. MIDI CC on a non-matching channel passes `Deck::Count` as a deck index (`core.ui.cpp:710-717`).
11. Manual vs code: Alt+Trig hold 2 s vs 1.5 s; Grit "Mix" described as overall gain but implemented as dry/wet; Grit Position (character) and Alt+Mix (feedback) and Tap+Cycle/Glow on deck B (pan speed/range) not documented.
13. `generator.cpp:144` modulus by zero on an empty deck (see Lessons).
14. `Flux::set_tempo_bpm` is never called, so Clocked delay is fixed at 120 BPM (see D33).
15. `Modulator::set_speed_norm` with sync on indexes `kFreqDiv[(1 - norm) * 9 - 1]`, which is -1 at norm = 1 (out of range). The plug-in keeps norm below 1.
16. `Modulator` leaves `_type`, `_freq_mult`, `_reset_count`, `_ticks_to_reset` and `_is_synced` uninitialised (relies on zeroed memory), and `LFO::_type`/`_amp` likewise.
17. DaisySP `WhiteNoise::Process` relies on signed integer overflow (undefined in C++); built with `-fwrapv` here.
18. `memory/wav.cpp` `read_cue_points` reads each cue offset as a `size_t` (`read_val<size_t>`). On the 32-bit Daisy that is the 4-byte field it means; on a 64-bit machine it reads 8 bytes (this port does not use that code and parses the cue chunk itself).
19. The cue point count is stored in a `uint8_t` (`Generator::cue_count()`), but the reader allows 256 points (`kMaxSlicePointCount`); 256 would read back as 0. This port keeps 255.
12. Credits spelling: "Litvinenko" (manual) vs "Lytvynenko" (CREDITS.md).
